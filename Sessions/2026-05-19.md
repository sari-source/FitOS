## User Request Summary

- The user asked about the feature where changing the workout plan should only affect future calendar days and should not touch previous days.
- I inspected the project and found an existing snapshot/history system using `fitos_plan_history` and `fitos_baseline`.
- The user clarified the desired behavior:
  - If today's workout has no logged sets, a workout plan change should update today's workout.
  - If today's workout has at least one logged set, today's workout should stay frozen and should not change with later workout plan changes.
  - Future dates should continue to use the latest plan.
  - Past dates should continue to use historical plan data.

## Bug Identified

- The previous snapshot lookup used snapshots with `snap.date <= dateStr` and selected the latest matching snapshot.
- Because snapshots are created when a change happens and contain the plan from before the change, a frozen date should generally resolve to the first snapshot on or after that date.
- The old logic could choose the wrong historical plan for older dates.
- The Log tab did not participate in historical/frozen plan resolution at all.

## Code Added

- Added `src/utils/effectiveState.js`.
- Added `hasLoggedSets(logs, dateStr)`.
  - Returns true when `logs[dateStr]` exists and has at least one entry.
- Added `shouldFreezeDate(date, logs)`.
  - Freezes a date when it is before today.
  - Freezes a date when it has at least one logged set.
  - Does not freeze today if no set has been logged.
  - Does not freeze future dates.
- Added internal `planIncludesLoggedExercise(plan, logsForDate)`.
  - Collects logged exercise names for the date.
  - Checks whether any day in a candidate plan includes one of the logged exercises.
  - This is used to avoid freezing today to an empty initial snapshot when the first plan load created a snapshot before any real workout plan existed.
- Added `getEffectiveStateForDate({ date, plan, macros, logs, planHistory, baseline })`.
  - Returns the current plan/macros when the date is not frozen.
  - For frozen dates, filters snapshots to those with `snap.date >= dateStr` and sorts them oldest to newest.
  - If the date has logged sets, chooses the first snapshot whose plan contains the logged exercise.
  - If the date has no logged sets but is frozen because it is in the past, chooses the first snapshot on or after the date.
  - If no matching snapshot exists and the current plan contains the logged exercise, falls back to the current plan.
  - Finally falls back to baseline plan/macros or current plan/macros.

## Converted Rest Day Bug Fix

- Updated `src/utils/effectiveState.js`.
- Replaced broad `planIncludesLoggedExercise(plan, logsForDate)` matching.
- Added exact-weekday matching with `planIncludesLoggedExerciseForDay(plan, logsForDate, dayName)`.
- Previous behavior:
  - A snapshot was considered valid if the logged exercise appeared anywhere in the weekly plan.
  - This allowed an old snapshot to match because another weekday had the same exercise, even though the target date's weekday was rest.
- New behavior:
  - A snapshot is considered valid for a logged date only if the target date's own weekday contains the logged exercise.
  - Current plan fallback also uses the same exact-weekday check.
- This should keep converted rest days visible in Calendar after logging an exercise.
